## 2. How to run it

The connected folder contains the working tree plus `chainlens-rebuild-v2.bundle`, which
carries the real branch history. It also still contains the v1 files (`app/`,
`test_app.py`, `requirements.txt`, `environment.yml`), because the sandbox could not
delete files there. Checking the branch out on a normal machine removes them:

```bash
cd <repo>
git fetch chainlens-rebuild-v2.bundle rebuild/v2:rebuild/v2
git checkout rebuild/v2      # this deletes the stale v1 files
```

Then, the path that was actually verified:

```bash
pip install -e ".[dev,localpg]"
CHAINLENS_LOCAL_PG=1 python scripts/migrate.py
CHAINLENS_LOCAL_PG=1 python -m eval.build_index
CHAINLENS_LOCAL_PG=1 python -m eval.run
python -m eval.report
python -m eval.gate
python -m pytest apps/api/tests -q      # 40 passed
python -m ruff check . && python -m ruff format --check .
python -m mypy                          # 58 files, clean
python scripts/build_eval_prototype.py
python -m http.server 8080 --directory apps/web/prototype   # then open evaluation.html
```

The compose path, **authored but never executed**:

```bash
docker compose -f infra/docker-compose.yml up --build
curl localhost:8000/health
```

Do not trust that second block until you have run it once. It is the single most likely
thing in this repository to be broken, because it is the only significant artifact that
was never executed.

## 7. Honest weak spots

**The embedding model is the weakest link and an interviewer will find it in a minute.**
The dense arm is TF-IDF plus SVD, not a sentence encoder. It is a real model and the
comparisons between configurations are internally valid, because every configuration uses
the same embedding space. But absolute Recall@6 of 0.676 is not a claim about what this
architecture does with `bge-small`, and the relative ordering could change: in particular,
the lexical arm matching the dense arm is a result that a proper encoder might well
reverse. Anyone reading this should assume the ranking of dense against lexical is
provisional.

**The evaluation is document-scoped, which is the easier setting.** Each question is
answered against its own contract. Corpus-wide retrieval across 29 similar distribution
agreements is materially harder and is not measured. If asked "would these numbers hold at
1,000 documents", the honest answer is that nothing here shows that.

**Relevance is derived from span overlap, which is generous at the margin.** A chunk that
clips one character of an annotated answer counts as relevant. `span_coverage@6` was added
precisely because Recall was flattering, and it is consistently lower. Quote both.

**The frontend has never been seen.** The Analyse screen now exists, the citation mark is
implemented, and a smoke test proves the marks land on the right characters. But no browser
was available in any session, so there is not one screenshot, and every claim about how it
looks is a claim about markup and tokens rather than pixels. A reviewer should assume the
layout has at least one embarrassing flaw that five minutes with a browser would find. The
three self-critiques at the end of `docs/taste-pass-analyse.md` are the ones visible from
the code; they are not the ones visible from the screen.

**The worker, the compose stack and CI have never run.** Three significant artifacts that
are authored and unverified. Each is individually plausible and collectively they are the
most likely source of a first-run failure.

**Clause detection is weaker than the design implies.** 417 of 1,509 chunks carry a clause
id, because the CUAD corpus is OCR-derived with irregular heading structure. On cleanly
typeset PDFs it should be much better, but that is a prediction, not a measurement.
